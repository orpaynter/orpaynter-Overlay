# Repository governance: operator runbook

**Draft only.** [`.github/rulesets/default-branch.json`](../../.github/rulesets/default-branch.json) is an importable GitHub repository branch-ruleset request body with `enforcement: disabled`. Files in a PR do **not** install or activate repository rules; importing this draft while disabled provides **no protection**. The [new-ruleset settings URL](https://github.com/orpaynter/orpaynter-Overlay/settings/rules/new?target=branch&enforcement=disabled) is an unsaved form, not proof of an existing rule. Only the repository owner should approve and perform settings activation and PR merges.

## Evidence and intended baseline

- Default branch: `main`. [Overlay source checks](../../.github/workflows/overlay-ci.yml) runs on PRs and pushes to `main`; its single job/check context is **`checks`** (not separate lint/test/build checks). It runs `npm ci --ignore-scripts --no-audit --no-fund`, `npm test`, and `npm run build` with telemetry disabled.
- GitHub Actions [main run 36946314547](https://github.com/orpaynter/orpaynter-Overlay/actions/runs/36946314547) and its [checks job 110649149622](https://github.com/orpaynter/orpaynter-Overlay/actions/runs/36946314547/job/110649149622) concluded **success**; [PR run 36946578395](https://github.com/orpaynter/orpaynter-Overlay/actions/runs/36946578395) also concluded **success**. These historical results do not prove this PR's check has run successfully or that future PRs will pass.
- This draft PR's [run 36948994548](https://github.com/orpaynter/orpaynter-Overlay/actions/runs/36948994548) reported **action_required**, not success, at the time of review. Confirm its gate and a subsequent successful `checks` before activation.
- The draft targets `~DEFAULT_BRANCH`, with no bypass actors: deny deletion and non-fast-forward pushes; require linear history, a PR with resolved conversations and **zero** approvals, and an up-to-date passing `checks` status. Zero approvals is a solo-operator bootstrap, **not independent review**. When an independent reviewer is available, change to one required approval and enable stale-review dismissal.
- `Restrict updates` is intentionally absent: that rule allows updates only by bypass actors, not merely “no direct pushes.” The PR requirement governs the normal path. No signatures, deployments, merge queue, code scanning, or bypass privilege is assumed.
- The check-run listing available here did not expose the GitHub Actions App's `integration_id`, so the draft requires the context but is **not bound to an expected App**. Verify the check-run producer and numeric App ID (e.g. via the check-runs API's `app.id` or GitHub's source selector), then add `integration_id` to the `checks` entry before activation. Do not guess an ID or mistake the workflow/job ID for an App ID.

## Before activation (owner)

1. Inspect repository and organization rulesets **and** classic `main` branch protection for overlap or conflicting requirements; inspect collaborators/reviewer availability. Read-only attempts to query rulesets, protection, and collaborators in this session returned HTTP 403, so their state is **unknown**, not absent.
2. Confirm the current PR's `checks` job actually concludes successfully and is selectable as the required check from **GitHub Actions**. Resolve any `action_required` approval/permission gate separately; a completed job alone is not proof of success. Verify the source App ID and put it in the draft or select the correct expected source in settings.
3. Confirm squash or rebase merging is still enabled for linear history (both were previously verified), and check that no existing rules block the intended PR path. Review the impact of requiring an up-to-date branch, including retriggering CI after base changes.
4. Review the publishing implications: after this workflow change lands on `main`, **future pushes to `main` will publish a Docker image**; version-tag and manual dispatch triggers remain available. Do not merge until this automatic behavior is approved.

## Activate in stages / recover

1. Review the [GitHub REST ruleset schema](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset), [creating/importing rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), and [available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). After resolving the checklist, import the JSON as a **disabled** repository branch ruleset or enter equivalent settings; confirm its target and controls in the UI. Do not create a duplicate if an equivalent rule already exists.
2. With owner approval, switch **that saved ruleset** to Active in settings; verify it actually applies to `main`. Open a small test PR and confirm direct updates/deletion/force pushes are blocked, while a passing, current GitHub Actions `checks` allows a PR merge through an enabled linear merge method. Do not use a production release or deployment as the test.
3. If the rule unexpectedly blocks valid PRs or conflicts with existing protection, the owner should return **that ruleset** to Disabled (or restore its previous enforcement), inspect the check source and overlap, and retry only after correction. Do not add bypass actors or weaken other rules to make a merge work; disabling this rule does not remove other existing protections.

AI agents may prepare code, tests, evidence, and a draft configuration; they must not activate settings, create credentials, receive bypass rights, merge PRs, or publish/deploy on the owner's behalf. This runbook is repository governance only, not authorization for corporate, legal, or financial operations.
